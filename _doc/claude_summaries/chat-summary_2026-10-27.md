### Is `--sabr` still needed with yt-dlp 2026.08.19? (youtube-downloader-app v2.6.1, docs only)

- **Question:** whether the `--sabr` flag (v2.5.0, added for the ~400 KB per-URL media cap on VPN/distrusted IPs) is still required now that yt-dlp 2026.08.19 is out.
- **Research:** the capped URLs came from the `android_vr` client, the only one still offering https formats in August. YouTube killed that client on 2026-08-17 ([yt-dlp #17456](https://github.com/yt-dlp/yt-dlp/issues/17456)); yt-dlp 2026.08.19 removed it from the defaults and added the `visionos` client plus `web_embedded` fallbacks ([#17461](https://github.com/yt-dlp/yt-dlp/pull/17461), [#17184](https://github.com/yt-dlp/yt-dlp/pull/17184)); 2026.10.21 added `tv_samsung` as a default. The SABR downloader ([PR #13515](https://github.com/yt-dlp/yt-dlp/pull/13515)) is still unmerged (last activity 2026-10-25); the maintainer now publishes a prebuilt [`sabr` pre-release](https://github.com/bashonly/yt-dlp/releases/tag/sabr) of the branch. The shared `venv` was already on 2026.10.26; `venv-sabr` was stale at 2026.07.04.
- **Verified on a commercial VPN exit** (the failure condition from 2026-08-18) with stable yt-dlp 2026.10.26 and the bgutil PO token provider: `yt-dlp -v -F` shows default clients `tv_samsung`, `visionos`, `web` and a full https DASH ladder from `tv_samsung`; direct downloads of a 3 MB audio and a 17 MB video format completed; the default `python src/main.py "<url>"` path downloaded a 229 MB 4K stream + audio, merged them, and fetched subtitles; a 300-comment paged fetch via `--write-comments` succeeded. No 403s, no `--sabr`. (The app's `--comments-only` was started on the same video but stopped — it has ~2.4 M comments — and replaced by the capped direct fetch.)
- **Conclusion:** `--sabr` is no longer the required path on VPN IPs; it is kept as a fallback in case the IP-reputation cap returns against the new clients. The retire-`venv-sabr` TODO is pushed to 2027-01 pending PR #13515.

### In plain English

**What is an "https ladder"?** When yt-dlp asks YouTube about a video, YouTube doesn't hand back one file. It hands back a menu: the same video at 144p, 240p, 360p, 480p, 720p, 1080p, 1440p and 2160p, plus separate audio tracks. Each rung of that ladder is a plain download link. "https" just means a normal direct download, the kind where you ask for the file and the server sends the bytes. The alternative YouTube is pushing is "SABR", its own streaming protocol that drips the video out in pieces and needs special client code to receive. Seeing the full ladder of plain links again, from the lowest to the highest quality, is the signal that YouTube is willing to serve whole files to this connection the ordinary way. In August that ladder had collapsed to a handful of links from one client, and those links were cut off after a few hundred kilobytes.

**Why was the "android" client the problem?** YouTube serves video differently depending on what kind of player asks for it. yt-dlp pretends to be one of several players: the web page, a TV app, a phone app, and so on. Each pretend player is called a "client". In August, YouTube had switched most clients over to its SABR-only streaming, so the only client still handing out plain download links was `android_vr`, the player used by VR headsets. Two things went wrong with it at once. First, YouTube had begun demanding a special proof-of-legitimacy ticket (the PO token) that our ticket-maker could not produce for that client. Second, on a VPN connection, YouTube cut off those ticketless links after a few hundred kilobytes, which is enough to pass yt-dlp's quick test fetch but never enough for a whole video. That is why we built the `--sabr` detour: it took a different road that wasn't subject to the cutoff. Then on 2026-08-17 YouTube shut the `android_vr` client down entirely, for everyone. Two days later yt-dlp replaced it with newer pretend players (`visionos`, later `tv_samsung`), and those get plain links that YouTube serves in full, even over a VPN. The road we were detouring around is gone, and a new one opened.

**Why are there still TODOs about folding in SABR or removing the flag?** The `--sabr` option depends on a version of yt-dlp that is not official yet. It is a proposed change (a "pull request") that a volunteer maintainer still has to review and approve, and as of late October 2026 that review has not happened. Because it is unofficial, it lives in its own separate install so it cannot interfere with the normal yt-dlp. That leaves two possible futures, and the TODOs cover both. If the change is merged into the official release, SABR support becomes built in, the separate install becomes pointless, and the flag could be retired by simply letting normal yt-dlp use SABR when it needs to. If the merge never happens but the VPN downloads keep working, the flag is an extra moving part nobody uses, and it can be removed outright. Either way we don't want to act now: the cutoff was YouTube deciding it distrusts VPN connections, and it could come back against the new clients at any time. The flag is a spare key kept in the drawer. The TODO just says to check the drawer again after January 2027 and decide whether the key is still worth keeping.

**The spare key is also out of date.** The separate `venv-sabr` install still holds the SABR build from July 2026 (version 2026.07.04), which is from before YouTube shut down the `android_vr` client and before yt-dlp added the newer players. The volunteer who maintains the SABR branch keeps it in step with the official releases, so the current SABR build (2026.10.21) already knows about those changes, but ours does not. If the cap ever comes back and `--sabr` is needed again, the old build might fail for reasons that have nothing to do with SABR itself. The README now says to re-run the one-line `pip install` from the "SABR downloads" section to refresh it, and notes that the maintainer also publishes a prebuilt `sabr` pre-release. Treat that refresh as a to-do for the next time the VPN starts failing, or sooner if you want the spare key to work when you reach for it. If the nodriver package gets reinstalled along the way, the one-time UTF-8 fix from the README must be applied again.

### Kick VOD "Requested resource not found" (youtube-downloader-app v2.6.2)

- **Symptom:** a legacy-UUID (v4) Kick VOD URL fetched metadata fine, then yt-dlp failed with `NOT_FOUND: Requested resource not found`; the `kick.com/.../videos/<legacy uuid>` URL didn't open in a browser either.
- **Diagnosis:** `api/v1/video/{uuid}` → 200, the metadata's `source` HLS `master.m3u8` → 200, `yt-dlp -F` → `NOT_FOUND`. yt-dlp 2026.10.26's `kick:vod` extractor now calls `POST web.kick.com/api/v1/stream/{id}/playback`, which only accepts UUIDv7 IDs, the reverse of the v2.4.1 problem. The downloader always passed yt-dlp a legacy-UUID URL.
- **Fix:** `kick_vod_downloader.py` now gives yt-dlp the `source` m3u8 (generic HLS, works for both ID styles). It falls back to the original URL only if that URL is UUIDv7, and otherwise raises a clear error before yt-dlp runs (`--chat-only` is unaffected). The chosen source is echoed with any query string stripped.
- **Verified:** `--video-only` on the failing VOD selected 1080p60, 5649 fragments, and downloaded ~1.4 GB at ~15 MiB/s before being stopped.
- **Files changed:** `youtube-downloader-app/src/kick_vod_downloader.py`, `youtube-downloader-app/CHANGELOG.md` (`[2.6.2]`), `youtube-downloader-app/README.md` (Kick VOD section), `youtube-downloader-app/CLAUDE.md` (replaced the yt-dlp #17284 TODO with a "video source" note), `_doc/programming_notes.md` (new entry).

### In plain English

Kick videos have an old-style and a new-style ID. Our script uses the old ID to ask Kick for the video's details, which still works. It used to hand that same old ID to yt-dlp to download the video, but the newest yt-dlp only understands new IDs, so it said "not found". The details Kick sends back already include a direct link to the video's playlist. The script now hands yt-dlp that link instead, and the download works no matter which kind of ID the URL had.
